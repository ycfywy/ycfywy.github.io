Tool Call 通常也是 assistant 输出，直接计算 token 级交叉熵。

Tool Response 保留为上下文，通常不作为监督目标。决定训练行为的是最终 token 序列和 mask，工具消息的字段名只是数据表达的一层。

01

先把三个环节分清楚

采集时执行工具；离线 SFT 时学习轨迹；部署时由运行器再次执行模型请求。

COLLECT

在环境里采集

强模型生成动作 → 解析 Tool Call → 执行 Bash / 编辑 → 返回真实结果 → 继续下一步。

TRAIN

对轨迹做监督

序列化消息，保留 observation；对 assistant token 建立 labels，再优化 next-token loss。

RUN

让模型闭环行动

模型生成调用请求，运行器执行并追加结果。重复交互，直到完成或触发终止条件。

模型生成的是工具请求。 Bash 的执行由外部程序完成；常规离线 SFT 不需要重新执行每条命令，也不需要对 shell 执行器反向传播。

一个目标：预测下一个动作 token

设 x 是渲染后的完整序列，m 是目标位置的监督 mask。以下展示常见的 token 平均形式；框架的 loss 聚合细节可能不同。

ℒSFT = − 1 / ∑ mt · ∑ mt log pθ(xt | x<t)
m = 1：预测这个 token　 /　m = 0：只保留为上下文

调用里的哪些部分有 loss？

工具名、参数名、参数值、调用格式，以及模型需要生成的结束标记。Bash 命令本身也在监督目标里。

工具结果真的“没有梯度”吗？

没有预测工具结果的直接 loss。但处理这些上下文的计算，仍可通过后续 assistant 的预测 loss 获得梯度。

06
什么时候从 SFT 走向 RL？
SFT 学习老师在老师历史里的动作。部署后模型遇到的是自己造成的状态，错误恢复和长程决策因此更难。
路线训练信号环境执行时机关键用途
轨迹 SFT教师动作的目标 token采集阶段建立工具协议与行动能力
成功筛选 + SFT通过验证的轨迹，仍用交叉熵采集、验证阶段减少对失败策略的模仿
在线 PPO / GRPO自己 rollout 的 reward / advantage训练 rollout 阶段优化闭环任务成功率
筛选成功轨迹并不会自动变成 RL。 如果筛选后仍在复现目标 token，优化目标还是 SFT。在线 RL 使用策略概率与回报；环境 token 仍需从策略目标中排除。
先做一个清晰的基线
真实环境采集 → 验证筛选 → assistant-only SFT → 闭环评测。先确认模型确实学到了调用和读取反馈。
再依据失败类型迭代
格式错：查模板；调用无效：查接口和数据；错误后卡住：补恢复轨迹；长期策略差：考虑在线 RL。



07
让训练数据经得起执行
以下为工程建议。比工具数量更重要的是接口语义、可复现环境和一致的历史。
用少量工具覆盖完整编码闭环
Bash、文件查看 / 编辑、长任务交互，以及结束动作。明确工作目录、超时、进程状态、stdin 与输出截断规则。
同时保存事件日志与模型可见上下文
记录仓库 base commit、环境版本、工具 schema、原始输出、可见输出、最终 patch、验证结果和终止原因。
保留真实反馈与有价值的恢复
老师发起调用，环境实际执行。成功轨迹中的测试失败与修正很有价值。不要删掉一次编辑却保留编辑后的 observation。
用实际可见历史处理长轨迹
可用完整轨迹，也可拆成“本轮之前的历史 → 当前 assistant”。逐轮样本只监督当前轮，避免历史动作被反复加权。截断与摘要应符合部署方式。
用闭环结果判断效果
检查调用合法率、执行有效率、任务通过率、步数和循环率。按仓库或任务族隔离评测，避免只看训练 loss。
